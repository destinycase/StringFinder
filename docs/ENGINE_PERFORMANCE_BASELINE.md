# StringFinder 엔진 성능 기준선

> 측정 기준 버전: **StringFinder 5.9.21** (5.9.22은 성능 진단 도구 개선 릴리스이며 검색 엔진은 변경하지 않음)
> 적용 릴리스: **5.9.25**. 아래 신뢰도 수정·JSON 최적화 측정은 버전 변경 전 5.9.24 작업본에서 수행했으며, 배포된 5.9.24의 측정값과 구분합니다. 과거 측정 태그는 유지합니다.
> 이 문서는 현재 제품의 공식 성능 기준과 릴리스 판정 규칙을 정의합니다. 과거 실험 및 미채택 최적화 후보는 [개발자 가이드](DEVELOPER_GUIDE.md)의 성능 검토 이력에 기록합니다.

## 공식 기준선

### 5.9.25 릴리스 검증

버전 변경 후 재빌드한 엔진으로 A–J를 실행해 전체 결과 159건, 건너뛴 파일 0건과 모든 공식 임계값 통과를 확인했습니다. `v5.9.25` 실행은 패키징 작업과 병행되어 Set A가 1.018초로 측정됐으므로 단독 실행 기록과 직접 비교해 회귀를 판정하지 않습니다. JSON 중복 키 검증의 최적화 효과는 아래의 별도 교차 측정 결과로 판단합니다. 기존 v5.9.21 공식 기준선과 과거 측정 태그는 보존합니다.

패키징 종료 후 재측정한 `v5.9.25-standalone`도 전체 결과 159건·건너뛴 파일 0건으로 통과했습니다. Set A 0.716초, 최대 첫 결과 지연 0.078초, 최대 RSS 155.8MB였습니다. 이때 전체 회귀 테스트의 종료 처리가 병행됐으므로 완전히 격리된 측정은 아닙니다. 릴리스 검증은 Python 514개 통과·2개 건너뜀, Rust 47개 통과이며 Ruff·Rust 포맷·Clippy 및 배포 EXE의 Qt/테마/엔진 스모크 테스트도 통과했습니다.

공식 A–J 벤치마크는 `python scripts/benchmark_performance.py`로 실행합니다. 측정 결과는 [벤치마크 히스토리](benchmark_history.md)에 행 단위로 누적합니다.

| 벤치마크 세트 | A–J, 10개 |
| 전체 매치 수 | 159 |
| 건너뛴 파일 | 0 |

벤치마크는 일반 텍스트, 대형 파일, 바이너리 혼합, 존재 여부 확인, JSON, XML, 무개행 파일, Excel을 포함합니다. 각 세트의 결과 수와 스킵 수는 회귀 검증을 위해 함께 확인합니다.

이번 실행은 공식 임계값을 모두 통과했고 매치 159건, 건너뛴 파일 0건을 확인했습니다. 기존 문서의 160건은 기록된 A–J 행의 합계와 달라 정정했습니다. Set A는 10,000개 소형 파일을 순회하는 세트이며, 이번 단일 실행의 Set A 시간은 직전 공식 기록보다 길게 측정됐습니다. 단일 실행만으로 성능 회귀를 판정하지 않으며, 반복 측정에서 같은 조건의 중앙값이 지속적으로 악화되는지 확인해야 합니다.

## 5.9.24 신뢰도 수정 작업본 재검증

공식 A–J는 3회 완주했고 모두 임계값을 통과했습니다. 세트별 결과 수는 매번 `100, 1, 50, 1, 1, 1, 1, 1, 1, 2`로 같고 건너뛴 파일은 0건입니다. 히스토리의 `v5.9.24-reliability-recheck`, `v5.9.24-reliability-recheck-cli`, `v5.9.24-reliability-recheck-cli-2` 행에 개별 측정값을 기록했습니다. 첫 실행은 QApplication을 유지하는 래퍼를 사용했고, 나머지 두 실행은 벤치마크 도구의 Qt 수명·워커 종료 대기를 보완한 뒤 공식 CLI로 실행했습니다. 측정 완료 시점은 워커의 완료 신호이며 정리 대기 시간은 검색 시간에 더하지 않습니다.

### JSON 키 관리 최적화 및 비용 분리

기본 중복키 금지 정책은 유지했습니다. 키 최적화 직전 작업본과 최적화 작업본을 같은 프로세스에 로드하고, 두 엔진 × 허용·금지를 번갈아 실행했습니다. 각 조합은 준비 실행 1회 후 18회 측정했으며 표의 단위는 ms, 값은 중앙값입니다. 두 바이너리와 두 정책에서 결과 내용·위치·길이 지문이 모두 같았습니다. 비교 대상은 중복키가 없는 문서이며, 중복키를 포함한 문서의 거부·허용 동작은 별도 회귀 테스트로 검증합니다.

| --- | ---: | ---: | ---: | ---: |
| 작은 객체 12만 개·반복 적중 | 27.007 | 19.640 | 18.488 | -27.3% |
| 작은 객체 12만 개·마지막 항목 적중 | 30.451 | 26.172 | 24.687 | -14.1% |
| 작은 객체 12만 개·존재만 확인 | 21.856 | 14.559 | 13.524 | -33.4% |
| 작은 객체 12만 개·결과 없음 | 29.840 | 25.634 | 24.142 | -14.1% |
| 이스케이프 키 포함 객체 2만 개 | 7.230 | 7.187 | 6.923 | -0.6% |

| 키 2만 개의 단일 객체 | 10.657 | 9.562 | 8.830 | -10.3% |

최적화 후 Rust 호출에서 금지·허용 차이는 위 표본에 대해 약 0.3~1.5ms였습니다. 이는 같은 코드의 검사 활성화에 따른 증분이며, 키 관리 구조를 도입한 전체 비용을 뜻하지 않습니다. 포장 경로의 무결과 측정에서 허용이 더 느린 것은 두 정책의 Python 문서 보존 방식 등도 포함되기 때문입니다. 따라서 허용하면 모든 경로가 반드시 빨라진다고 일반화하지 않습니다.

키 최적화 후 일반 JSON 경로를 수정 전 HEAD 바이너리와 추가 비교한 값은 다음과 같습니다. Python 포장 코드는 양쪽에 같은 현재 코드를 사용했습니다. 이전 바이너리는 중복키 금지 계약을 구현하지 않았으므로, 이는 동일 계약 최적화 비교가 아닌 기존 속도 대비 참고치입니다.

| 표본 | 수정 전 HEAD 엔진(ms) | 최적화 후 금지(ms) |
| --- | ---: | ---: |
| 작은 객체·반복 적중 | 117.299 | 45.020 |
| 작은 객체·마지막 항목 적중 | 65.268 | 34.431 |
| 작은 객체·존재만 확인 | 97.492 | 22.891 |
| 작은 객체·결과 없음 | 284.034 | 280.059 |

| 키 2만 개의 단일 객체 | 9.212 | 9.871 |

표본과 시스템 상태에 따라 값이 달라집니다. 특히 큰 단일 객체는 검사하지 않았던 HEAD보다 약 0.66ms(+7.2%) 증가했으므로 모든 표본에서 원래 속도를 회복했다고 선언하지 않습니다. Python 누락 방지 파서는 이번 키 최적화에서 변경하지 않았습니다.

최적화 후 공식 A–J는 `v5.9.24-json-key-opt`, `v5.9.24-json-key-opt-2`로 기록했습니다. 두 실행 모두 159건·건너뛴 파일 0건이며 임계값을 통과했습니다. 이 공식 세트만으로 위 JSON 특수 검색 비교를 대체할 수는 없습니다.

재실행 예시:

```powershell
python tools/benchmark_json_policy.py --backend native --repeats 18
python tools/benchmark_json_policy.py --compare-engine C:/bench/before/sf_engine.pyd --backend normal --repeats 18
```

## 릴리스 판정 규칙

새 버전은 다음 조건을 모두 만족해야 합니다.

- 모든 공식 세트의 기대 매치 수 이상을 반환한다.
- 건너뛴 파일이 없어야 한다. 의도된 스킵을 검증하는 별도 테스트는 예외로 기록한다.
- 세트별 시간·지연·RSS가 프로젝트에 정의한 임계값 이내여야 한다.
- JSON/XML 손상 입력, Excel 오류 입력, 존재 여부 확인 경로의 결과 무결성이 유지되어야 한다.
- 반복 측정에서 결과 파일 집합, 매치 수, 스킵 사유가 일치해야 한다.

단일 실행의 수 ms 차이만으로 성능 회귀를 확정하지 않습니다. 회귀 의심 시 동일 장비에서 warm-up을 제외한 반복 측정의 중앙값과 P95를 비교합니다.

## 측정 환경과 해석

측정값은 Windows, Python, PySide6, Rust 확장 모듈 및 현재 장비 상태의 영향을 받습니다. OS 캐시, 백그라운드 작업, 엔진 초기화 상태에 따라 변동할 수 있습니다. RSS는 측정 구간의 관측값이며 장비 전체의 OOM 한계를 의미하지 않습니다.

서로 다른 장비나 데이터셋에서 얻은 값은 직접 비교하지 않습니다. 버전 간 공식 비교는 동일 데이터셋·동일 실행 조건·동일 판정 규칙을 사용한 경우에만 유효합니다.
