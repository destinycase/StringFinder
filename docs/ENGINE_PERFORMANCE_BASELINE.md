# StringFinder Engine Performance Baseline

회귀 비교 기준선: **StringFinder v5.9.1**
최신 측정: **StringFinder v5.9.5 (2026-09-17)**

측정일: 2026-09-06 18:19 KST

환경: Windows, Python 3.12.9, PySide6 6.10.1, Rust extension 5.9.1

이 문서는 이후 버전의 성능 회귀를 판단하기 위한 현재 기준선이다. 이전 버전의 상세 측정값은 [벤치마크 기록](benchmark_history.md)에 보존한다.

## 측정 방법

### 엔진 단독

`python tools/benchmark_engine.py`를 독립적으로 3회 실행한다. 각 실행은 임시 파일을 생성하고 경로별로 한 번 준비 실행한 뒤 3회 측정한다.

- 시간: 각 실행에서 얻은 median의 중앙값
- RSS delta: 세 실행에서 관측한 최댓값
- JSON 무매치 폴백: Rust 검색 후 Python 정밀 폴백까지 포함한 애플리케이션 경로
- 일반 텍스트: 파일 초반의 충분한 매치와 결과 상한이 적용되므로 전체 파일 처리량으로 해석하지 않음

### GUI·워커 통합

`python scripts/benchmark_performance.py v5.9.1`로 표준 A–J 데이터셋을 실행한다. 시간뿐 아니라 예상 적중 수와 스킵 여부를 함께 검증하며, 세부 결과는 [벤치마크 기록](benchmark_history.md)에 누적한다.

### Excel 전용

`python tools/benchmark_excel.py`로 대량 문자열 셀의 일반 검색, 마지막 셀 매치, 존재 여부 검색을 측정한다. 통합문서 생성 시간은 제외한다.

## 5.9.3 후속 리소스 QA — 2026-09-08

재현 명령: `python tools/validate_parallel_resources.py`. 제품 소스·배포 바이너리는 변경하지 않고 기존 엔진을 측정했다. 각 사례는 새 자식 프로세스에서 실행하며 입력 생성 시간은 제외한다. RSS는 검색 프로세스를 5ms 간격으로 샘플링한 절대값으로 Rust 할당도 포함하지만, 순간 최고값을 놓칠 수 있다. 시간은 단일 실행 참고값이며 기존 A–J와 다른 워크로드다.

JSON/XML은 각각 약 32MiB 파일 8개이며 파일 끝에 매치 1개를 배치했다. XLSX는 파일당 40,000행 × 4열의 긴 문자열과 마지막 행 매치 1개를 담았고, 압축된 파일 크기는 970,178바이트다. 종류별 별도 병렬 검색이며 여러 형식을 동시에 실행하는 시험은 아니다.

취소 사례마다 같은 프로세스에서 새 이벤트로 재검색하여 8개 파일의 정상 결과 복구를 확인했다. 완료 결과는 파일 집합·중복·파일당 매치 수를 검증하고, 예산 부족은 `ERR_RESOURCE_BUDGET` 사유까지 확인한다. 프로세스당 2GiB RSS, 시스템 여유 2GiB, 90초 실행 시간에 별도 QA 감시 장치를 두었으며 이번 실행에서는 작동하지 않았다. 실제 OOM이나 제품의 전체 메모리 중단 경계를 강제로 발생시킨 시험은 아니다.

평가: JSON/XML은 예산을 줄이면 속도와 메모리를 교환하며 정상 결과를 유지했다. XLSX는 디스크 크기 8MiB 미만이라 기존 예약의 적용 대상이 아니었다. 압축률이 높은 Excel의 메모리 추정은 추가 검토 대상이지만, 이번 측정만으로 크래시나 배포 차단 결함으로 판정하지 않는다. 원본 크기에 기반한 예산을 실제 메모리의 하드 캡으로 설명해서는 안 된다.

추가 QA: 기본 제외된 stress·chaos 10개 통과. 긴 경로 검색은 정확한 파일/매치/스킵을, Excel 벤치마크는 정확히 2개 매치를 확인하도록 테스트를 강화했다. 모든 마커를 포함한 전체 테스트는 **393개 통과, 1개 스킵**이었다. Windows의 chmod 반복은 ACL 읽기 권한 박탈을 보장하지 않으며, 기존 tracemalloc 시험은 Rust 전체 메모리 검증으로 간주하지 않는다.

배포 EXE UI 검증은 5.9.3 창 실행, 기존 세션 표시, 별도 검색 탭 생성까지 확인했다. 이후 앱 제어 도구의 승인 검토가 크레딧 부족으로 거절되어 중단했다. 실제 EXE에서의 검색·중지·재검색·정렬·미리보기·내보내기 및 새 세션 저장/복원은 아직 수동 확인이 필요하다. Python 미설치 Windows 환경도 검증하지 않았다. 소스 테스트 통과를 이 항목들의 대체 증거로 사용하지 않는다.

후속 확인(2026-09-08): 사용자가 위 배포 EXE 사용자 흐름을 직접 체크했다고 보고했다. 이는 사용자 수동 확인 기록이며 자동화 검증으로 집계하지 않는다. Python 미설치 환경의 확인 여부는 별도로 보고되지 않았다.

## 압축 XLSX 메모리 예산 후보 검토 — 2026-09-08

작업 전 QA 변경은 `83325da`로 커밋하고 origin/main에 푸시했다. 아래 검토는 제품 코드나 배포본을 변경하지 않은 별도 프로토타입이다.

**종료 상태:** 아래는 당시 실험의 방법·결과 기록이다. 제품 미채택으로 검토를 종료했으며 실험용 Cargo feature, 엔진 코드, 전용 테스트와 벤치마크 도구는 제거했다. 현재 저장소에는 측정 기록만 남기므로 아래 언급된 실험 파일/API는 제공되지 않는다. 설치 엔진과 배포 EXE 및 기본 검색 동작은 변경하지 않았다.

당시 Python 하네스는 ZIP 중앙 디렉터리의 원본 크기 합계만 읽고 시트 XML을 압축 해제하거나 셀을 파싱하지 않았다. 후보는 디스크 크기 또는 ZIP 원본 크기가 8MiB 이상이면 `max(디스크 × 8 + 128MiB, ZIP 원본 합계 × 2 + 128MiB)`를 예약했다. 계수는 비교용 가설이며 실제 메모리 상한으로 검증된 값이 아니다.

기존 엔진의 단일 파일 검색을 동일한 8스레드 Python 하네스에서 호출하고, 후보에만 메타데이터 검사 및 공유 예약을 추가했다. 기존 Rust 디렉터리 검색과 실행 경로가 다르므로 앞선 A–J나 리소스 QA 시간과 직접 비교하지 않는다. 기존/후보 순서를 교차하고 준비 실행을 제외한 5회 중앙값을 기록했다. 2048MiB 후보는 후속 5회 측정으로 실행 순서가 교차되지 않아 캐시 영향이 남는다. 모든 실행에서 파일별 실제 매치 내용과 개수가 일치했다.

결과 이력은 `benchmark_history.md`에 기록했다. 고압축 입력은 파일당 디스크 약 0.93MiB, ZIP 원본 합계 48,436,544바이트로 후보 예약량은 220.39MiB였다. 256MiB 예산에서는 한 파일씩 처리하여 RSS가 약 451.5→102.1MiB로 줄었지만 시간은 0.3692→1.774초로 늘었다. 2048MiB 예산에서는 8개 동시 예약이 가능했고 0.4028초였다. RSS는 동일 프로세스의 5ms 샘플 최고값이며 반복 실행의 allocator 잔류 페이지가 영향을 줄 수 있다.

소형 입력은 예약 대상에서 제외해도 ZIP 검사 비용이 남아 8파일 기준 0.0021→0.0034초였다. 파일당 메타데이터 검사 중앙값은 약 0.18~0.20ms다. 이는 Python ZIP 구현과 로컬 warm-cache의 측정값으로, 네이티브 구현이나 네트워크 파일의 비용을 대신하지 않는다. 고압축 데이터에 대한 효과는 있지만 **검색 속도 영향이 없다는 조건은 충족했다고 볼 수 없어 제품 적용을 보류**한다.

### 권장 후속 설계

- ZIP 기반 예상량을 기존 Rust 공유 예약에 통합하는 네이티브 후보를 먼저 측정한다. Python에서 모든 파일을 사전 순회하거나 셀을 한 번 더 파싱하는 방식은 피한다.
- 여유 메모리가 충분하면 기존 병렬성을 유지하고, 부족할 때만 대기하도록 기존 정책을 유지한다. 예산을 무조건 작게 고정하면 이번 시험처럼 속도가 크게 낮아진다.
- XLSX/XLSM 및 ZIP 기반 XLSB와 OLE 기반 XLS를 구분한다. 압축 해제 크기만으로 희소한 시트 좌표, sharedStrings, 셀 객체 오버헤드까지 완벽히 추정할 수는 없다.
- 메타데이터 읽기 실패를 새로운 무조건 스킵으로 만들지 않는다. 기존 Excel 오류 분류·검색 결과 계약을 유지해야 한다. ZIP64, 암호화·손상 ZIP, 많은 엔트리, 크기 오버플로 및 검사 후 파일 변경도 검증한다.
- 취소된 대기 작업의 예약 반환, 단일 파일·병렬 경로·누락 방지 검색 간 정책 일관성, 일반/존재/정확 일치 결과를 함께 검증한다.
- 제품 반영 전 소형 파일 다량, 고압축·저압축·다중 시트·sharedStrings·희소 좌표 입력의 반복 비교가 필요하다. 현재 합성 입력 두 종류의 일치만으로 실제 운영 파일 전체의 무결성을 보장하지 않는다.

### 네이티브 후보 구현 및 판정 (2026-09-08)

당시 실험용 Rust `xlsx-budget-prototype` Cargo feature로 ZIP32 예상량을 기존 공유 예약에 연결했다. 기본값은 비활성이었고 일반 빌드에는 적용하지 않았다. 설치된 `sf_engine.pyd`와 배포 EXE는 교체하지 않았다. 이 후보는 최종 미채택되어 코드에서 제거했다.

`xlsx_budget.rs`는 말미 4KiB 버퍼를 먼저 읽어 중앙 디렉터리와 끝 레코드를 재사용한다. 긴 ZIP 주석은 최대 65,557바이트까지 확인하고, 디렉터리는 1MiB/8,192개 엔트리까지만 허용한다. 압축 데이터 일부가 말미 버퍼에 포함될 수는 있지만 압축 해제나 시트 XML 파싱을 수행하지 않는다. 원본 크기 합계를 비교용 계수에 적용하며 구조를 확정할 수 없으면 기존 디스크 크기 추정으로 돌아간다. 새 의존성과 unsafe 코드는 추가하지 않았다.

ZIP64·분할 ZIP·한도를 넘는 디렉터리는 이 후보에서 크기 힌트를 제공하지 않는다. 메타데이터는 신뢰할 수 있는 실제 할당량이 아니고, 검사 이후 파일 교체나 희소 셀 좌표를 완전히 통제하지 못한다. 기본 오류 파서는 기존 Calamine이 담당한다. 이 제한을 해결한 전체 ZIP/OOM 방어로 설명하지 않는다.

벤치마크는 **같은 Rust 디렉터리 API**로 기존/후보를 별도 프로세스에서 순서를 교차해 각 3회 실행했다. 각 프로세스는 준비 실행 1회 후 3회 중앙값을 반환하고, 프로세스 중앙값의 중앙값을 이력에 기록했다. 파일 이름·행·매치 값·매치 종류를 정규화해 모든 반복과 엔진 간 일치를 확인했다. RSS는 각 프로세스 5ms 샘플 최고값으로 순간 최대를 보장하지 않는다. 앞선 Python 스레드 하네스와 시간 값을 직접 비교하지 않는다.

판정: 고압축 8파일에서 256MiB 예산은 RSS 416.6→79.2MiB로 줄었지만 0.16654→0.84059초로 느려졌다. 여유 예산 2048MiB에서는 0.18468→0.18858초로 차이가 작았다. 그러나 소형 200파일은 0.02838→0.03901초 및 0.02716→0.03286초로 느려져 **기본 적용을 보류**했다. 첫 구현에서도 소형 파일 비용이 관찰됐고 버퍼 재사용 후에도 남았다. 메모리 절감만으로 검색 속도 조건을 충족했다고 판단하지 않는다.

전용 회귀 테스트는 기본 5.9.3에서 보호 동작 5개가 실패하고 기존 오류 분류 2개가 통과한 뒤, 후보에서 7개 모두 통과했다. 일반/긴 ZIP 주석, data descriptor, 충분한 예산의 실제 매치, 작은/큰 파일 혼합, 손상 ZIP 사유, 디렉터리 존재 검색을 확인했다. Rust 기본 42개·feature 활성 45개, Clippy(all features) 및 Ruff를 통과했다. 후보 Rust 테스트에는 예약 대기 취소·반환 후 재사용 및 잘못된 디렉터리/ZIP64 sentinel 폴백이 포함된다. 기본 Python 전체는 393개 통과·8개 스킵(기존 환경 스킵 1개 + 후보 전용 7개)이며 후보 전용 테스트는 별도로 로드한 실험 엔진에서 실행했다. 전체 Python suite를 실험 엔진으로 검증했다는 의미는 아니다.

당시에는 별도 release 후보 바이너리를 로드해 기존 설치 엔진과 비교했다. 실험 소스와 도구 제거에 따라 더 이상 유효하지 않은 빌드·실행 명령은 남기지 않는다.

다음 개선을 시도한다면 Calamine이 이미 읽는 메타데이터를 재사용하여 별도 파일 열기/읽기를 없애는 쪽을 먼저 검토한다. 이는 파서 통합 범위가 커지므로 별도 작업으로 다룬다. 임의의 압축 파일 최소 크기 컷오프를 추가해 측정만 빠르게 만들거나, 이번 후보를 기본 활성화하는 변경은 하지 않았다.

#### 메타데이터 재사용 후속 검토 (2026-09-08)

현재 사용하는 Calamine 0.33.0 소스를 확인한 결과, **공개 API만으로 이미 파싱한 ZIP 중앙 디렉터리를 직접 재사용하는 방식은 적용할 수 없다.** `xlsx/mod.rs`의 `Xlsx.zip`은 비공개이며, `Reader::new`는 `ZipArchive::new` 직후 공유 문자열과 스타일을 읽는다. 따라서 완성된 workbook을 받은 뒤 예약을 획득하는 방법은 초기 메모리 적재를 보호하지 못한다. `worksheet_cells_reader`도 workbook 생성 이후 사용하는 API이므로 이 문제의 해결책은 아니다.

`open_workbook_from_rs`는 사용자 제공 `Read + Seek`를 받을 수 있다. 이를 통해 파일 핸들을 공유하거나 읽기 버퍼를 재사용하는 실험은 가능하지만, Calamine의 중앙 디렉터리 파싱 결과를 재사용하는 API는 아니다. 별도 크기 검사와 예약 획득을 Excel 열기 경로에 통합해야 하며, 이 변경만으로 소형 파일 성능 회귀가 해소된다고 판단할 근거는 아직 없다.

후속 구현 후보와 승인 조건은 다음과 같다.

- 의존성 수정 없는 후보: 하나의 파일 핸들로 크기 힌트를 읽고, 예약을 획득한 다음 같은 reader를 Calamine에 전달한다. 파일 재열기는 줄일 수 있지만 메타데이터 중복 해석은 남는다. 먼저 별도 실험으로 비용 감소를 측정한다.
- 직접 재사용 후보: Calamine에 ZIP 생성 후 공유 문자열 적재 전 예약 훅 또는 사전 생성 archive를 받는 API가 필요하다. 현재 공개 API 밖의 변경이므로 의존성 포크를 기본 제품에 도입하지 않았다. 별도 유지보수 범위 합의가 필요하다.
- 어느 후보든 예약은 workbook 초기 적재 전 획득하고 실제 검색 종료까지 유지해야 한다. 취소·파싱 오류·panic 경로에서 예약 반환, 기존 skip 분류와 검색 결과 일치, 디렉터리/파일 목록/존재 확인 경로를 검증해야 한다.
- 기존과 동일한 소형 다수 파일 및 압축률 높은 파일의 충분/제한 예산 비교를 반복한다. 기존 성능 회귀 기준을 만족하기 전에는 기본 활성화하지 않는다. ZIP 크기 합은 여전히 예상량이며 전체 OOM 방어를 보장하지 않는다.

이번 후속 검토에서는 실행 코드·설치 바이너리·배포 파일을 변경하지 않았다. 신규 성능 측정도 없으므로 벤치마크 히스토리에 측정 행을 추가하지 않았다.

#### 동일 파일 핸들 분리 실험 (2026-09-08)

이후 `xlsx_budget::tests::compare_shared_handle` 무시 테스트로 공개 API의 동일 핸들 전달을 실제 검증했다. 실험용 크기 검사 함수를 파일 핸들을 받는 내부 함수로 분리했으며, 검색 경로의 호출 방식은 바꾸지 않았다. 세 방식 모두 Calamine으로 모든 시트 range를 읽고 셀 데이터 전체가 같은지 비교한다. 동일 핸들 방식은 검사 후 커서를 처음으로 되돌린 다음 `open_workbook_from_rs`로 전달한다.

release 빌드, 동일 파일 warm-cache, 방식 순서를 순환한 10라운드 중 첫 라운드를 제외하고 라운드별 100회 평균의 중앙값을 사용했다. 4,829바이트 소형 fixture를 세 번 실행했을 때 동일 핸들은 별도 핸들보다 약 23~31% 빨랐지만, 검사 없는 기준보다 약 5~10% 느렸다. XML 주석으로 확장 크기를 늘린 fixture도 데이터 일치를 확인했으나, 이는 다수 셀/공유 문자열 부하를 대표하지 않는다. 측정값은 히스토리에 기록했다.

**판정: 별도 파일 열기를 줄이는 효과는 확인했지만 제품 채택 근거로는 부족하다.** 이 실험에는 병렬 검색, 공유 예약 대기, 실제 검색 매칭, 취소 및 오류 경로 통합이 없다. 다음 단계는 opt-in 후보에서 예약을 초기 적재 전에 유지하면서 같은 핸들을 전달하고 기존 전체 검색 벤치마크와 회귀 테스트를 반복하는 것이다. 설치 바이너리와 배포 파일은 그대로 유지한다.

당시 수동 성능 테스트는 ZIP32 fixture를 입력받아 명시적으로 실행했다. 이 테스트도 검토 종료 시 제거했다. 위 후속 설계는 재개 시 참고 조건이며 현재 진행 중이거나 제품에 반영된 작업이 아니다.
### 5.9.5 벤치마크 평가 (2026-09-17)

5.9.5 엔진으로 기존 엔진·Excel 벤치마크를 실행했다. 일반 텍스트는 1MiB 0.0089초, 32MiB 0.0096초였고 취소 모니터 추가 비용은 0.0004초였다. JSON 스트리밍은 0.0396~0.0414초, 존재 여부 확인은 0.0301초, 무매치는 0.2583초였다. XML 스트리밍은 0.0718초였다. 400,000셀 Excel은 무매치 0.2567초, 마지막 셀 매치 0.3514초, 존재 여부 확인 0.2350초였다.

각 케이스는 워밍업 후 중앙값이며 결과 개수와 예상 매치 여부를 검증한다. 수치는 동일 장비 회귀 기준이지 절대 성능 보증이 아니다. 로그 파일 저장 권한 경고가 있었으나 검색 결과와 측정에는 영향이 없었다.
