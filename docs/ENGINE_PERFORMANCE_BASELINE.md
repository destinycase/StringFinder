# StringFinder 6.1.1 검색 성능 기준

**기준 버전: 6.1.1 (안정 버전)**

이 문서는 현재 성능 비교에 사용할 측정값, 실행 조건과 판정 규칙만 관리합니다. 과거 최적화·회귀·미채택 후보와 이전 기준선은 [개발자 가이드 9절](DEVELOPER_GUIDE.md#9-검색-성능-개선과-회귀-검토-이력), 실행별 원본은 [벤치마크 히스토리](benchmark_history.md), 일반 변경은 [개발 이력](DEVELOPMENT_HISTORY.md)에서 확인합니다.

## 1. 기준선 요약

- **측정 대상:** 6.1.1 Python 소스와 프로젝트 Rust 엔진. 배포 EXE의 시작·압축 해제 시간을 측정한 기록이 아닙니다.
- **측정 방법:** 준비 실행 1회 후 별도 프로세스에서 A–J를 5회 반복. 준비 실행은 통계에서 제외했습니다.
- **결과:** 측정 5회 모두 검색 결과 159건·건너뛴 파일 0건이며 공식 임계값을 통과했습니다.
- **검색 시간 합계 중앙값:** **1.235초**. 실행별 합계는 1.324, 1.235, 1.258, 1.227, 1.230초입니다. 각 실행의 합계를 먼저 구한 뒤 중앙값을 계산했으며 세트별 중앙값의 합과 다릅니다.
- **대표 값:** Set A 중앙값 0.735초, 가장 긴 세트별 첫 결과 지연 중앙값 0.079초(Set E), 측정 5회 중 최대 관측 RSS 150.9MiB(Set E).
- **판정 범위:** 공식 A–J의 정상 검색 처리 기준입니다. 모든 파일 형식·인코딩·검색어의 정확성이나 모든 검색 경로의 속도를 보장하지 않습니다. 안정 버전 지정도 무결점 보증은 아닙니다.

## 3. 세트별 측정값

시간·지연 단위는 초, RSS는 MiB입니다. 히스토리의 `MB` 표기는 측정 코드의 `1024 × 1024` 나눗셈에 따른 값입니다. 중앙값·범위는 저장된 소수점 셋째 자리 원본에서 계산했습니다.

| --- | ---: | ---: | ---: | ---: | ---: |
| A · 소형 파일 10,000개 | 0.735 | 0.729~0.841 | 0.046 | 52.5 | 100 |

| D · 존재 확인 조기 종료 | 0.022 | 0.022~0.023 | 0.022 | 48.3 | 1 |
| E · ASCII 대형 파일 | 0.079 | 0.077~0.084 | 0.079 | 150.9 | 1 |
| F · JSON 일반 검색 | 0.035 | 0.035~0.036 | 0.035 | 76.4 | 1 |

## 4. 공식 판정 기준

수치의 원본은 `scripts/benchmark_performance.py::check_thresholds()`입니다. 문서만 수정해 코드의 기준을 바꾸지 않습니다. 아래 임계값은 여유를 둔 통과 기준이며, 이 값을 넘지 않았다는 이유만으로 이전 버전 대비 회귀가 없다고 결론내리지 않습니다.

| 세트 | 최대 검색 시간(s) | 최대 첫 결과 지연(s) | 최대 RSS(MiB) |
| --- | ---: | ---: | ---: |
| A | 3.0 | 1.5 | 200 |
| B | 1.5 | 0.8 | 200 |
| C | 1.0 | 0.8 | 150 |
| D | 1.5 | 1.5 | 150 |
| E | 1.0 | 0.8 | 200 |
| F | 5.0 | 2.0 | 600 |
| G | 3.0 | 2.0 | 300 |
| H | 1.5 | 1.5 | 200 |
| I | 5.0 | 2.0 | 500 |
| J | 3.0 | 2.0 | 300 |

코드는 기대 결과 수 이상과 건너뛴 파일 0건도 확인합니다. 새 기준선과의 비교에서는 결과가 불필요하게 늘어난 경우도 검사하며, 속도를 평가하기 전에 파일 집합·내용·위치·건너뛴 사유를 별도 회귀 테스트로 확인합니다.

진행 보고 간격의 표준편차(Jitter)는 A–E 0.2초, F–H/J 0.3초, I 0.5초를 넘으면 경고합니다. 현재 코드에서는 실패 조건이 아닙니다. 보고 간격 표본이 부족해 0으로 표시될 수 있으므로 0이 UI의 무지연을 증명하지 않습니다.

## 5. 이후 비교·갱신 규칙

1. 동일 장비·데이터·설정·검색 경로에서 준비 실행을 제외한 반복 중앙값과 범위를 비교합니다. 결과 상한에 도달한 검색과 파일 전체 처리량을 섞지 않습니다.
2. 기준선과 비교본을 가능하면 교대로 실행합니다. 빌드·테스트와 겹친 실행, 준비 실행, 배포 EXE와 소스 실행, 서로 다른 장비는 구분합니다.
3. 5회로 안정적인 P95를 확정하지 않습니다. 차이가 의심되면 반복 수를 늘리고 부하·캐시·원인 계측을 함께 확인합니다.
4. 공식 통과 여부와 기준선 대비 비용 증가를 각각 보고합니다. 검색 계약을 완화하거나 검색 파일·결과를 줄여 얻은 속도를 같은 조건의 개선으로 인정하지 않습니다.
5. 새 기준선을 채택할 때 버전·소스/배포본 구분·엔진 해시·실행 조건·원본 태그를 함께 갱신합니다. 이전 기준과 최적화 판단은 개발자 가이드로 옮기며 히스토리를 덮어쓰지 않습니다.

실행 절차는 [개발자 가이드 7.5절](DEVELOPER_GUIDE.md#75-벤치마크와-릴리스-검증)을 따릅니다. 다음 예시는 태그 구분 방식이며, 기본 설정 격리·데이터 준비는 별도로 해야 합니다.

```powershell
python scripts/benchmark_performance.py v6.1.1-baseline-warmup
1..5 | ForEach-Object { python scripts/benchmark_performance.py "v6.1.1-baseline-r$_" }
```

## 6. 측정하지 않는 범위

- F/G는 JSON/XML 파일의 **일반 텍스트 검색**입니다. JSON/XML 특수 검색과 Python 누락 방지 검색은 별도 측정합니다.
- 결과 목록·미리보기 렌더링, 세션 복원, 시작 화면 지연, EXE 압축 해제와 전체 앱 실행 시간을 포함하지 않습니다.
- 시간은 워커 실행 요청부터 종료 시그널 수신까지입니다. 데이터 생성·프로세스 시작·히스토리 저장 시간은 검색 시간 합계에 포함하지 않습니다.
- RSS는 10ms 간격으로 관측한 현재 프로세스 메모리이며 순간 피크나 모든 자식 프로세스의 메모리를 보장하지 않습니다.
- 새 기준선 채택은 과거 버전보다 빨라졌다는 선언이 아닙니다. 과거 개선·추가 비용과 비교 한계는 개발자 가이드에서 관리합니다.
