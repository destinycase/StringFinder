# StringFinder Engine Performance Baseline

기준 버전: **StringFinder v5.9.1**

측정일: 2026-09-06 18:19 KST

환경: Windows, Python 3.12.9, PySide6 6.10.1, Rust extension 5.9.1

이 문서는 이후 버전의 성능 회귀를 판단하기 위한 현재 기준선이다. 이전 버전의 상세 측정값은 [벤치마크 기록](benchmark_history.md)에 보존한다.

## 측정 방법

### 엔진 단독

`python tools/benchmark_engine.py`를 독립적으로 3회 실행한다. 각 실행은 임시 파일을 생성하고 경로별로 한 번 준비 실행한 뒤 3회 측정한다.

- 시간: 각 실행에서 얻은 median의 중앙값
- RSS delta: 세 실행에서 관측한 최댓값
- JSON 무매치 폴백: Rust 검색 후 Python 정밀 폴백까지 포함한 애플리케이션 경로
- 일반 텍스트: 파일 초반의 충분한 매치와 결과 상한이 적용되므로 전체 파일 처리량으로 해석하지 않음

### GUI·워커 통합

`python scripts/benchmark_performance.py v5.9.1`로 표준 A–J 데이터셋을 실행한다. 시간뿐 아니라 예상 적중 수와 스킵 여부를 함께 검증하며, 세부 결과는 [벤치마크 기록](benchmark_history.md)에 누적한다.

### Excel 전용

`python tools/benchmark_excel.py`로 대량 문자열 셀의 일반 검색, 마지막 셀 매치, 존재 여부 검색을 측정한다. 통합문서 생성 시간은 제외한다.

## 직전 배포 기준선과 비교

| 항목 | v5.8.9 | v5.9.1 | 변화 |
|---|---:|---:|---:|
| A–J 전체 시간 | 1.622 s | 0.861 s | -46.9% |
| 전체 적중 수 | 159 | 159 | 동일 |
| 건너뛴 파일 수 | 0 | 0 | 동일 |

엔진 단독 경로에서는 33.28MiB 일반 텍스트가 v5.8.9보다 0.6ms 길었고, 나머지 기존 경로는 0.6~3.4% 짧았다. 이 정도 절대 차이는 실행 환경 변동 범위이며, 통합 경로의 임계치·적중 수·스킵 조건도 모두 충족했으므로 체감 가능한 성능 회귀나 검색 결과 무결성 회귀는 확인되지 않았다.

## 기준선 판정 규칙

후속 버전은 최소한 다음 조건을 충족해야 한다.

- A–J 데이터셋의 적중 수가 159건보다 적지 않아야 한다.
- 예기치 않은 건너뛴 파일이 없어야 한다.
- `benchmark_performance.py`의 시간·메모리 임계치를 모두 통과해야 한다.
- JSON/XML 구문 검증, 결과 상한, 취소 처리 등 검색 무결성 정책을 성능을 위해 우회하면 안 된다.
- 단일 측정에서 수 ms가 변한 것만으로 회귀나 개선을 확정하지 않는다. 절대 차이, 반복 측정, 적중·스킵 결과를 함께 판단한다.

## 유지한 최적화와 제외한 후보

- 검색 완료 채널로 취소·진행 감시 스레드를 즉시 종료한다.
- 여러 검색 루트는 하나의 `WalkBuilder` 병렬 워커 풀로 순회한다.
- 파일 스냅샷의 불필요한 핸들 복제와 Excel 시트 목록의 중복 복제를 제거했다.
- Excel 문자열 셀 제로카피 후보는 40만~100만 셀 교차 측정에서 개선과 회귀가 일관되지 않아 적용하지 않았다.
- ASCII 전용 비교 단순화는 유니코드 특수 대소문자 미탐 위험 때문에 적용하지 않는다.

## 해석의 한계

- 단일 Windows 장비와 합성 데이터 기준이다.
- 운영체제 캐시, 백그라운드 작업, 저장장치 상태에 따라 수 ms 수준의 차이가 생길 수 있다.
- RSS delta는 프로세스의 절대 최대 메모리가 아니라 측정 구간의 증가량이다.
- 실제 운영 데이터, cold-cache, 네트워크 드라이브 성능은 별도로 측정해야 한다.

## 5.9.3 후속 리소스 QA — 2026-09-08

재현 명령: `python tools/validate_parallel_resources.py`. 제품 소스·배포 바이너리는 변경하지 않고 기존 엔진을 측정했다. 각 사례는 새 자식 프로세스에서 실행하며 입력 생성 시간은 제외한다. RSS는 검색 프로세스를 5ms 간격으로 샘플링한 절대값으로 Rust 할당도 포함하지만, 순간 최고값을 놓칠 수 있다. 시간은 단일 실행 참고값이며 기존 A–J와 다른 워크로드다.

JSON/XML은 각각 약 32MiB 파일 8개이며 파일 끝에 매치 1개를 배치했다. XLSX는 파일당 40,000행 × 4열의 긴 문자열과 마지막 행 매치 1개를 담았고, 압축된 파일 크기는 970,178바이트다. 종류별 별도 병렬 검색이며 여러 형식을 동시에 실행하는 시험은 아니다.

| 종류 | 공유 예산 MiB | 모드 | 반환 파일 / 스킵 | 소요 초 | 샘플 최고 RSS MiB |
|---|---:|---|---|---:|---:|
| JSON | 1024 | 완료 | 8 / 0 | 0.0726 | 168.7 |
| JSON | 160 | 완료 | 8 / 0 | 0.2068 | 52.5 |
| JSON | 160 | 50ms 후 취소 | 4 / 0 | 0.1136 | 53.1 |
| JSON | 1 | 개별 예산 부족 | 0 / 8 | 0.0073 | 22.7 |
| XML | 1024 | 완료 | 8 / 0 | 0.0783 | 245.6 |
| XML | 160 | 완료 | 8 / 0 | 0.2109 | 55.1 |
| XML | 160 | 50ms 후 취소 | 4 / 0 | 0.1126 | 55.2 |
| XML | 1 | 개별 예산 부족 | 0 / 8 | 0.0058 | 21.4 |
| XLSX | 1024 | 완료 | 8 / 0 | 0.1972 | 398.5 |
| XLSX | 160 | 완료 | 8 / 0 | 0.1915 | 400.2 |
| XLSX | 160 | 50ms 후 취소 | 0 / 0 | 0.2105 | 367.6 |
| XLSX | 1 | 작은 압축 파일 | 8 / 0 | 0.2056 | 386.8 |

취소 사례마다 같은 프로세스에서 새 이벤트로 재검색하여 8개 파일의 정상 결과 복구를 확인했다. 완료 결과는 파일 집합·중복·파일당 매치 수를 검증하고, 예산 부족은 `ERR_RESOURCE_BUDGET` 사유까지 확인한다. 프로세스당 2GiB RSS, 시스템 여유 2GiB, 90초 실행 시간에 별도 QA 감시 장치를 두었으며 이번 실행에서는 작동하지 않았다. 실제 OOM이나 제품의 전체 메모리 중단 경계를 강제로 발생시킨 시험은 아니다.

평가: JSON/XML은 예산을 줄이면 속도와 메모리를 교환하며 정상 결과를 유지했다. XLSX는 디스크 크기 8MiB 미만이라 기존 예약의 적용 대상이 아니었다. 압축률이 높은 Excel의 메모리 추정은 추가 검토 대상이지만, 이번 측정만으로 크래시나 배포 차단 결함으로 판정하지 않는다. 원본 크기에 기반한 예산을 실제 메모리의 하드 캡으로 설명해서는 안 된다.

추가 QA: 기본 제외된 stress·chaos 10개 통과. 긴 경로 검색은 정확한 파일/매치/스킵을, Excel 벤치마크는 정확히 2개 매치를 확인하도록 테스트를 강화했다. 모든 마커를 포함한 전체 테스트는 **393개 통과, 1개 스킵**이었다. Windows의 chmod 반복은 ACL 읽기 권한 박탈을 보장하지 않으며, 기존 tracemalloc 시험은 Rust 전체 메모리 검증으로 간주하지 않는다.

배포 EXE UI 검증은 5.9.3 창 실행, 기존 세션 표시, 별도 검색 탭 생성까지 확인했다. 이후 앱 제어 도구의 승인 검토가 크레딧 부족으로 거절되어 중단했다. 실제 EXE에서의 검색·중지·재검색·정렬·미리보기·내보내기 및 새 세션 저장/복원은 아직 수동 확인이 필요하다. Python 미설치 Windows 환경도 검증하지 않았다. 소스 테스트 통과를 이 항목들의 대체 증거로 사용하지 않는다.

후속 확인(2026-09-08): 사용자가 위 배포 EXE 사용자 흐름을 직접 체크했다고 보고했다. 이는 사용자 수동 확인 기록이며 자동화 검증으로 집계하지 않는다. Python 미설치 환경의 확인 여부는 별도로 보고되지 않았다.
