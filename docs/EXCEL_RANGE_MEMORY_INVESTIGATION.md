# Excel의 거대한 사용 범위: 저비용 방어 가능성 조사

## 결론과 작업 범위

전체 Excel 파일을 별도로 사전 검사하는 방식은 채택하지 않는다. 추가 ZIP/XML 읽기가 발생하기 때문이다.

현재 calamine 0.33.0에는 시트 전체의 직사각형 배열을 만들지 않고 셀을 순차적으로 읽는 공개 API가 있다. 따라서 라이브러리 수정 없이도 XLSX/XLSM의 거대한 빈 영역 할당을 피할 후보가 존재한다. 다만 정상 파일의 속도와 기존 검색 계약까지 검증한 제품 구현은 아직 아니다. 이번 작업은 로컬 라이브러리 코드 조사와 독립 파서 실험이며, 배포 엔진·Python 검색 경로를 변경하지 않았다. 이전 빈 셀 비교 최적화 변경은 유지했다.

## 코드에서 확인한 사항

- Rust의 `src/rust_engine/src/excel_search.rs`는 일반 검색과 존재 확인 모두 `worksheet_range()`를 호출한다.
- calamine의 XLSX 경로는 `worksheet_cells_reader()`의 `next_cell()`로 값을 수집한 후 `Range::from_sparse()`를 호출한다.
- `Range::from_sparse()`는 실제 비어 있지 않은 셀들의 최소·최대 좌표를 찾고, 그 사이 전체 직사각형에 대해 `vec![T::default(); len]`을 할당한다. 현 API에 사용자 메모리 예산이나 할당 직전 콜백을 전달할 수 없다.
- Python의 설치된 python-calamine 0.6.2는 `get_sheet_by_name()` 이후 `iter_rows()`를 제공한다. 이 시점에는 시트 배열 할당이 이미 끝난다. 셀 단위 reader는 Python API에 노출되어 있지 않다.
- Rust의 공개 `worksheet_cells_reader()`는 기존 공유 문자열·서식·날짜 변환을 사용하는 동일 파서다. 별도 XML 구현이나 두 번째 파일 전체 검사는 필수가 아니다.
- 통합 문서 초기화 시 공유 문자열과 서식은 여전히 읽는다. 셀 reader를 사용해도 모든 Excel 메모리 부족 위험이 사라지는 것은 아니다.

## 독립 실험

실험 코드·원시 측정은 무시 대상인 `samples/excel_range_memory_261003/stream_probe/`, `probe_stream.py`, `stream_probe_results.json`에 있다. 기존 표본은 변경하지 않았다. 스프레드시트 도구에 해당 Rust API 비교 기능이 없으므로 실제 엔진과 같은 calamine을 사용하는 독립 Rust 프로그램으로 검증했다.

11개 표본, 방식별 7회, 총 133회 실행했다. 각 파서는 별도 프로세스에서 Windows Job Object의 프로세스당 커밋 메모리 768MiB 제한을 상속받았다. 시트명·셀 좌표·디코딩 값의 개수와 정렬된 내용 해시를 비교했다. 기존 방식의 할당 실패가 확인된 2,500만~1억 셀 표본은 셀 reader만 실행하고 두 실제 값과 예상 좌표를 검사했다.

아래 시간은 통합 문서 열기·전체 값 읽기·비교용 값 수집·정렬·해시까지의 중앙값이다. GUI 검색 시간이나 제품 최적화 효과가 아니다. RSS는 프로세스 전체의 최대값이다.

| 표본 | 기존 배열 방식 | 셀 reader | 최대 RSS 기존 → reader |
| --- | ---: | ---: | ---: |
| 1,000만 셀 범위, 실제 값 2개 | 0.1711초 | 0.00044초 | 310.1 → 5.0MiB |
| 빈 결과 수식 다수, 넓은 범위 | 0.2003초 | 0.0275초 | 310.2 → 5.0MiB |
| 고정 값 10만 개 | 0.1013초 | 0.1025초 | 24.3 → 18.3MiB |
| 짧은 수식 결과 10만 개 | 0.1113초 | 0.1156초 | 24.4 → 18.3MiB |
| 긴 수식 결과 10만 개 | 0.1138초 | 0.1191초 | 24.4 → 18.3MiB |
| 1억 셀 범위, 실제 값 2개 | 재실행하지 않음 | 0.00044초 | reader 5.0MiB |

직접 비교 가능한 8개 표본에서 값·좌표·개수가 일치했다. 나머지 3개 거대 범위 표본도 예상한 두 실제 값을 읽었다. 먼 좌표의 인접한 두 셀과 먼 위치의 서식만 있는 대조군도 정상 처리했다.

10만 값 표본의 reader 시간은 약 1.2~4.6% 증가했다. 이 실험에는 비교용 문자열 복사·정렬이 포함되어 있고 항상 기존 방식부터 실행했으므로 제품 회귀율이나 통계적으로 확정된 차이로 해석하지 않는다. 작은 Excel 다수·실제 검색·UI·손상 문서·날짜/오류 셀의 검색 계약은 이 실험만으로 검증되지 않았다. 기존 빈 결과 수식 표본에는 `<v>` 캐시가 없는 경우가 포함되므로 실제 Excel에서 재계산한 모든 빈 수식을 대표하지 않는다.

## 권장 구현 방향

1. **기존 API 바로 앞에서 검사만 추가하는 것은 불가능하다.** 같은 범위를 먼저 알아내려면 별도 읽기가 필요하거나, calamine 내부를 수정해야 한다. 설치된 Cargo 캐시·Python 패키지를 직접 수정하지 않는다.
2. 우선 XLSX/XLSM에 대해 공개 셀 reader를 쓰는 별도 후보를 제품 테스트에서 검증한다. 파일 크기만으로 안전 여부를 판정하거나 `<dimension>`만 믿고 파일을 제외하지 않는다.
3. 정상 파일은 기존 방식 유지, 위험 파일만 reader 사용이라는 혼합 방식은 아직 확정하지 않는다. 위험 판별용 두 번째 읽기 없이 구현할 수 있는지, 잘못된 범위 메타데이터도 방어되는지 확인해야 한다. 단순 메타데이터 분기만으로 안전을 보장할 수 없다.
4. 누락 방지 검색은 기존 Python의 유니코드 비교 정책을 유지해야 한다. 셀 reader 결과를 Python에 연결하는 경우 파일마다/셀마다 FFI 호출을 반복하지 않고 묶음 전달하는 방식을 계측한다. 일반 검색의 비교 정책으로 대체하지 않는다.
5. 결과 순서, 중복 좌표의 최종 값 처리, 비어 있는 값, 서식만 있는 셀, 날짜·시간·오류·수식 캐시, 손상 시트의 부분 결과, 취소, 파일당 제한, 존재 확인 조기 종료를 기존 계약과 비교한다. 시트 XML에 적힌 순서는 기존 배열의 행·열 순서와 항상 같다고 가정하지 않는다.
6. XLS/XLSB는 이번 공개 XLSX API의 적용 대상이 아니다. 별도로 조사하고 미해결 범위를 안내한다. 공유 문자열 등 초기 할당 위험에도 프로세스 격리가 필요한지 별도로 판단한다.

## 적용 판정 조건

- 작은 Excel 다수·값이 밀집된 표·수식 많은 표를 변경 전후 교대 실행하고, 준비 실행 제외 후 검색 시간과 최대 메모리를 비교한다.
- 일반/누락 방지 × 존재 확인 on/off 및 정확 일치 계약을 모두 검증한다.
- 결과의 개수뿐 아니라 시트·셀·내용·부분 검색 안내가 같아야 한다.
- 지속적인 정상 파일 속도 저하가 있으면 일괄 전환하지 않는다. 위험 파일의 범위를 잘라 검색하거나 오류를 ‘결과 없음’으로 반환하지 않는다.
- 기존 자동 테스트 통과와 별개로 실제 배포 경로·프로세스 취소·메모리 실패 격리를 확인한다.

현재 판정은 **추가 읽기를 피할 기술적 후보를 확인했고, 거대한 빈 영역에는 효과가 컸으나, 속도 무회귀와 전체 검색 무결성을 검증한 제품 수정은 아직 아니다**이다.
